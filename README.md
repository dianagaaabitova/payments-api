# Payments API

Асинхронный сервис обработки платежей на Python 3.12. FastAPI принимает платёж и возвращает `202 Accepted`. Обработчик имитирует ответ платёжного шлюза за 2–5 секунд, с вероятностью успеха 90%, затем отправляет подписанный webhook. Статусы платежа и доставки уведомления доступны через API.

## Запуск

Понадобится Docker с Compose.

```bash
cp .env.example .env
docker compose up -d --build --wait
```

- [Swagger UI](http://localhost:8000/docs) с кнопкой **Authorize** и схемой исходящего webhook.
- [OpenAPI](http://localhost:8000/openapi.json).
- [RabbitMQ Management](http://localhost:15672). Локальная учётная запись из примера — `payments` / `payments`.

Сервис `migrate` применяет миграции Alembic до старта API и consumer. PostgreSQL и RabbitMQ используют именованные тома. Для остановки выполните `docker compose down`. Порты API и RabbitMQ Management доступны на loopback; PostgreSQL и AMQP доступны внутри Docker-сети.

## API

Оба платёжных эндпоинта и `GET /health/ready` требуют `X-API-Key`. Swagger UI и OpenAPI доступны без ключа. Readiness проверяет подключение к PostgreSQL и наличие таблиц. API продолжает принимать платежи во время недоступности RabbitMQ.

Используйте ключ из `.env` и замените URL в примере своим HTTPS-адресом, принимающим POST.

```bash
export API_KEY=local-payments-api-key-change-me

curl -i http://localhost:8000/api/v1/payments \
  -H "X-API-Key: $API_KEY" \
  -H 'Idempotency-Key: order-42-attempt-1' \
  -H 'Content-Type: application/json' \
  -d '{
    "amount": "1490.00",
    "currency": "RUB",
    "description": "Заказ №42",
    "metadata": {"order_id": 42},
    "webhook_url": "https://example.com/webhooks/payments"
  }'
```

```json
{
  "payment_id": "38a41d1a-9fae-46b4-9720-dae4e9751951",
  "status": "pending",
  "created_at": "2026-11-20T09:00:00Z"
}
```

Ответ содержит заголовок `Location`. По этому адресу можно получить текущий статус и детали, включая число технических сбоев шлюза в поле `gateway_failures`.

```bash
curl http://localhost:8000/api/v1/payments/38a41d1a-9fae-46b4-9720-dae4e9751951 \
  -H "X-API-Key: $API_KEY"
```

Повтор с тем же ключом и теми же нормализованными данными возвращает исходную квитанцию `202`, даже после обработки. Изменение данных под уже использованным ключом возвращает `409`. Порядок полей JSON и представление одной и той же суммы, например `1490` и `"1490.00"`, эквивалентны. Для клиентских интеграций предпочтительна строка суммы, чтобы сохранить точность при сериализации в языке клиента. Допустимая сумма положительна, с точностью до двух значащих десятичных знаков и до 16 цифр в целой части.

Ошибки API: `401` для отсутствующего или неверного ключа, `404` для неизвестного UUID, `409` для конфликта идемпотентности, `413` для тела больше 64 КиБ, `422` для невалидных данных и `503` при временной недоступности БД. При `503` или сетевом таймауте повторите создание с исходным ключом и телом.

### Webhook

```json
{
  "event_id": "38a41d1a-9fae-46b4-9720-dae4e9751951",
  "payment_id": "38a41d1a-9fae-46b4-9720-dae4e9751951",
  "status": "succeeded",
  "amount": "1490.00",
  "currency": "RUB",
  "processed_at": "2026-11-20T09:00:04Z"
}
```

Получатель проверяет `X-Webhook-Signature` по исходным байтам тела до разбора JSON. Формат заголовка — `sha256=<hex>`, где `hex` вычисляется через HMAC-SHA256 с `WEBHOOK_SIGNING_SECRET`. Используйте постоянный `X-Webhook-Id` (то же значение, что `event_id`) для идемпотентной обработки и отвечайте `2xx` после сохранения результата. Для данного платежа одно финальное уведомление, поэтому идентификатор webhook совпадает с UUID платежа.

Любой `2xx` подтверждает доставку. HTTP-ошибки, таймауты и ошибки DNS или соединения расходуют попытку. Всего **три отправки**, включая первую, с паузами 2 и 4 секунды по умолчанию. Перенаправления отключены. Сервис проверяет все DNS-адреса и подключается к проверенному IP, сохраняя исходное имя для HTTP и TLS. При сбое установления соединения сервис пробует другой проверенный IP в пределах того же таймаута. После отправки запроса дальнейший повтор идёт по обычному расписанию webhook. Частные, локальные и специальные адреса блокируются по умолчанию. `WEBHOOK_ALLOWED_HOSTS` принимает JSON-массив точных имён и нужен только для доверенных внутренних получателей, например для интеграционного теста. Compose использует локальные учётные данные из примера. Для общего окружения задайте собственные ключи и пароли, HTTPS и ограничьте исходящий трафик на сетевом уровне.

## Архитектура и гарантии

- `payments/api/` содержит HTTP API. `payments/contracts.py` задаёт схемы API, событий и webhook.
- `payments/persistence/` содержит модели PostgreSQL и операции записи платежей и Outbox.
- `payments/delivery/` отвечает за RabbitMQ и HTTP-доставку webhook. `payments/processing.py` управляет состояниями и повторами, а `payments/worker.py` запускает обработчик и издателя Outbox.
- **Атомарный приём.** Уникальность ключа обеспечивает PostgreSQL. Платёж и его первое событие фиксируются в одной транзакции. Публикация не входит в HTTP-запрос.
- **Transactional Outbox.** Издатели выбирают готовые события с `FOR UPDATE SKIP LOCKED`. После подтверждения маршрутизованной публикации RabbitMQ издатель отмечает запись опубликованной. Сбой между подтверждением и записью отметки может привести к дублю. У каждого события собственное расписание повторов публикации с паузами от 2 до 60 секунд. Пока неработающий маршрут ждёт повтора, готовые события других маршрутов публикуются. Очереди `payments.new` и `payments.dlq` долговечны, сообщения публикуются как persistent.
- **Идемпотентный обработчик.** Блокировка строки сериализует изменения одного платежа. Результат шлюза фиксируется до HTTP-вызова. Успешный webhook или сохранённый счётчик попыток делают повтор обработки того же сообщения безопасным. Подтверждение сообщения отправляется после коммита. Если получатель успел принять webhook, а коммит сорвался, уведомление может прийти снова с тем же ID.
- **Повторы и DLQ.** Consumer фиксирует попытку и запись следующего события или DLQ в одной транзакции. Планирование хранится в `outbox.available_at` и переживает перезапуск. Финальный отказ webhook виден в API как `webhook_status=exhausted`, а DLQ содержит UUID платежа, номер попытки и код ошибки. `status=failed` означает отказ имитируемого шлюза и тоже порождает webhook. Ошибочные сообщения брокера отправляются через DLX. У технических ошибок шлюза отдельный лимит в три попытки. После исчерпания платёж переходит в `failed`, событие уходит в DLQ, клиент получает уведомление о финальном результате. При временной ошибке БД сообщение возвращается в очередь без расходования попытки. Если постоянная ошибка БД мешает сохранить состояние, сообщение остаётся в DLQ для ручного восстановления после устранения причины.
- **Эксплуатация.** Для диагностики используются логи consumer, неопубликованные строки Outbox и очередь DLQ. Для DLQ предусмотрен ручной разбор, поскольку повторная отправка исчерпанного уведомления требует отдельной операции со своим контрактом. Compose перезапускает API, consumer и инфраструктурные сервисы после аварийного завершения. Развёртывание состоит из одного PostgreSQL и одного RabbitMQ, поэтому потеря узлов или дисков выходит за пределы его гарантий.

```bash
docker compose logs -f consumer
docker compose exec api alembic check
docker compose exec rabbitmq rabbitmqctl list_queues name messages consumers
```

## Проверки

Ruff и MyPy запускаются одной командой из корня проекта:

```bash
uv run --locked pre-commit run --all-files
```

Команда проверяет код и форматирование Ruff, затем типы через MyPy. Чтобы запускать эти проверки автоматически при каждом коммите, один раз выполните `uv run --locked pre-commit install`.

Тесты запускаются отдельно. Быстрый прогон:

```bash
uv run --locked pytest -q
```

Для всех тестов поднимите отдельный Compose-проект. В нём проверяются API, конкурентная идемпотентность, точность суммы, подпись webhook, повторы, DLQ и восстановление после сбоев.

```bash
API_PORT=18000 RABBITMQ_MANAGEMENT_PORT=25672 WEBHOOK_ALLOWED_HOSTS='["test"]' \
  docker compose -p payments-integration --profile test run --build --rm --use-aliases test

docker compose -p payments-integration --profile test down
```

Изменение схемы локально выполняется через Docker-сервис с тем же окружением, что и приложение. Для генерации ревизии на хосте понадобятся доступный PostgreSQL и экспортированный `DATABASE_URL`.

```bash
DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/payments \
  uv run alembic revision --autogenerate -m "describe change"
```
